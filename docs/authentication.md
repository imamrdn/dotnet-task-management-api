# Authentication and Authorization

How the API identifies callers (authentication) and what they are allowed to do (authorization).

## Authentication Overview

The API uses **JWT Bearer authentication** with symmetric signing (HMAC SHA-256). A client logs in,
receives a short-lived **access token** (JWT) and a longer-lived **refresh token**, and sends the
access token as `Authorization: Bearer <token>` on protected requests.

Configuration is read from `Program.cs` via `AddJwtBearer`, with these validation parameters:

- `ValidateIssuer = true`
- `ValidateAudience = true`
- `ValidateLifetime = true`
- `ValidateIssuerSigningKey = true`

The signing key comes from `Jwt:Key`. If it is missing or blank, startup throws
`InvalidOperationException("JWT key is not configured")` — the app fails fast rather than running
with an insecure default.

## Registration

`POST /api/auth/register` → `AuthService.RegisterAsync`:

1. `RequestValidation.EnsureValid(request)` validates name, email, and password.
2. Email uniqueness is checked (`DuplicateResourceException` → `400` if taken).
3. A new `User` is created with `Role = "User"` (regular users are never created as Admin here).
4. The password is hashed (see below) and stored in `User.PasswordHash`.
5. Returns `200` with `data: null`. Registration does **not** log the user in.

## Login

`POST /api/auth/login` → `AuthService.LoginAsync`:

```text
credentials (email + password)
    → validate request
    → find user by email
    → verify password hash
    → generate access token (JWT)
    → generate refresh token, hash it, store in DB
    → return { token, refreshToken }
```

If the user is not found, the password does not match, or the stored hash is malformed
(`FormatException`), the result is the same generic `401` with message
`"Invalid email or password"`. A warning is logged without revealing which part failed.

## Password Storage

Passwords are hashed with ASP.NET Core Identity's `PasswordHasher<User>` (PBKDF2-based, salted),
registered in DI as `IPasswordHasher<User>`. Plain passwords are never stored and never logged.
Verification uses `VerifyHashedPassword`. No password value is ever written to logs.

## Access Token

Generated by `AuthService.GenerateJwtToken`. Claims:

| Claim | Value |
| --- | --- |
| `ClaimTypes.NameIdentifier` | user id |
| `ClaimTypes.Email` | user email |
| `ClaimTypes.Name` | user name |
| `ClaimTypes.Role` | user role (`User` or `Admin`) |

- **Lifetime:** 1 hour (`expires: DateTime.UtcNow.AddHours(1)`).
- **Issuer / Audience:** from `Jwt:Issuer` and `Jwt:Audience` (both default to
  `TaskManagement.Api` in `appsettings.json`).
- **Algorithm:** HMAC SHA-256 with the symmetric key from `Jwt:Key`.

Controllers read the user id from `ClaimTypes.NameIdentifier`. In `TasksController` this uses
`int.TryParse`; a missing or non-numeric claim throws `UnauthorizedAccessException` (`401`).

## Refresh Token

Refresh tokens are opaque random strings, not JWTs.

- **Generation:** 64 random bytes from `RandomNumberGenerator`, Base64-encoded.
- **Storage:** only the **SHA-256 hash** of the token is stored (`RefreshToken.TokenHash`,
  unique index). The raw token is returned to the client but never stored.
- **Lifetime:** 7 days (`ExpiresAt = UtcNow.AddDays(7)`).
- **Active check:** `RefreshToken.IsActive => RevokedAt is null && ExpiresAt > DateTime.UtcNow`.

`POST /api/auth/refresh` → `AuthService.RefreshAsync`:

1. Hash the incoming refresh token and look it up.
2. If not found or not active → `401 "Invalid refresh token"`.
3. **Rotate:** mark the old token `RevokedAt = UtcNow`, record `ReplacedByTokenHash`, and insert a
   new refresh token.
4. Issue a new access token for the same user.
5. Return `{ token, refreshToken }`.

`POST /api/auth/logout` → `AuthService.LogoutAsync`:

1. Hash the token and look it up.
2. If it does not exist, do nothing (still `200`).
3. If it exists and is not already revoked, set `RevokedAt = UtcNow`.
4. Returns `200` with `data: null`.

### What is implemented vs not implemented

Implemented:

- Refresh token generation, hashing before storage, rotation on refresh, and revocation on logout.
- Reuse of an already-revoked or expired refresh token is rejected with `401` (the `IsActive`
  check).

**Not implemented:** automatic reuse **detection** / token-family revocation. The
`ReplacedByTokenHash` column is written during rotation, but nothing currently reads it to detect
whether a revoked token is being reused and to invalidate the whole family. Reusing an old token
is simply rejected; it does not trigger broader revocation. This is documented as current
behavior, not as a feature.

## Authorization

Authentication answers *who* the caller is; authorization answers *what* they may do.

- **Authentication** is provided by `UseAuthentication`, which validates the JWT and populates
  `HttpContext.User`.
- **Authorization** is provided by `UseAuthorization`, which enforces `[Authorize]` and policies.

Mechanisms in use:

| Mechanism | Where | Effect |
| --- | --- | --- |
| `[Authorize]` | `TasksController` (class-level) | Any authenticated user may call task endpoints. |
| Policy `AdminOnly` | `Program.cs`: `RequireRole("Admin")` | Applied to `UsersController`, `CategoriesController`, and admin task routes. |
| Resource ownership | `TaskService` | Task queries are scoped by `UserId == current user`; other users' tasks appear as `404`. |

The `AdminOnly` policy is registered once and referenced as `[Authorize(Policy = "AdminOnly")]`.
A caller without the `Admin` role receives `403` (authenticated but not permitted); a caller
without a valid token receives `401`.

Resource ownership is enforced in the service layer, not only in the controller, so it cannot be
bypassed by calling the service directly. Admin task reports (`/api/tasks/admin/*`) intentionally
read across all users.

## Secret Configuration

`Jwt:Key`, `Jwt:Issuer`, and `Jwt:Audience` come from configuration. `appsettings.json` contains
empty/placeholder values only; real secrets must be supplied locally or per environment:

- **Local:** .NET User Secrets (`dotnet user-secrets set "Jwt:Key" "..." --project TaskManagement.Api`).
- **CI:** environment variables (`Jwt__Key`, `Jwt__Issuer`, `Jwt__Audience`) — see
  `.github/workflows/ci.yml`.
- **Production:** environment variables, e.g. `Jwt__Key`.

Never commit real keys. The signing key must be long enough for HMAC SHA-256 (32+ characters).
